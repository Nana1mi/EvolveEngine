# Spark-X2.6-1.7B Q8_0 serving compatibility pilot

This opt-in overlay is for the tied-embedding Spark2.5-architecture, 28-layer, fused-QKV Q8_0 checkpoint tested on ARM64 / GB10. It is **not** a general Spark GGUF implementation: a separate output head, a different tensor inventory or quantization, and distributed serving are rejected. It does not change the original weights, add an SGLang production dependency to EvolveEngine, or change an existing P1 study lock. Compatibility is not an optimization result.

## What is changed

- `spark2_5_gguf.py` checks the full GGUF tensor inventory, shape and storage type before loading. It keeps the packed Q8_0 bytes, maps the tied embedding and both normalization tensors per block, and splits the fused QKV tensor along the output dimension into native Q/K/V shard IDs.
- `apply_overlay.py` applies the matching native SGLang changes to a **new copy** of the exact SGLang revision `b2ce7f8811bc40fd0d67000030c22edbbe0f2a37`. It checks the original source hashes and requires strict parameter consumption. The head-wise output gate uses the GGUF quantization path for this checkpoint, not the normal BF16 path.
- `audit_weights.py` validates tensor metadata for every tensor, compares normalization values exactly, and compares sampled dequantized Q8_0 rows (including Q/K/V boundaries) to the pre-quantization Safetensors checkpoint. Run the audit once for each admitted weight digest. This is a mapping check and not end-to-end quality signoff.

## Reproduce the smoke

1. Prepare a throwaway copy of the pinned SGLang source and apply `python apply_overlay.py <copied-source-root>`. Keep the unmodified source and SHA-256 of the actual GGUF for provenance. Obtain the original config, tokenizer and chat template from the corresponding checkpoint; stage them next to the actual GGUF. Do not copy or alter a running deployment.
2. In an isolated Python runtime with CUDA 13 and the GB10 GPU exposed, the smoke used Torch `2.14.1+cu130`, Torchvision `0.29.1+cu130`, `sglang-kernel 0.4.11`, FlashInfer Python `0.7.4`, Transformers `5.19.0`, Tokenizers `0.23.1`, Hugging Face Hub `1.31.0` and `gguf 0.19.0`. The CUDA runtime and lower-level dependencies came from the node's existing ARM64 container with per-run dependency overrides, **not** from an image rebuilt at the pinned commit. Lock the full dependency set separately before any timed comparison. Do not ignore incompatible kernel versions.
3. Run `python audit_weights.py <q8-gguf> <matching-original-safetensors-dir>` in a CPU container with Torch, GGUF and Safetensors. The reference directory must contain `model.safetensors.index.json` and both shards.
4. Mount patched source at `/patched` and set `PYTHONPATH` to start with `/patched/python`. In a disposable GPU container, mount the staged config and Q8_0 file read-only at `/model`, set `HF_HUB_OFFLINE=1`, use no external network or host port, and run `bash smoke_entry.sh`. It uses TP1, Triton attention, bounded context/KV allocation and no prefill/decode graph; it checks that `/v1/chat/completions` returns actual `READY` content, `finish_reason=stop`, and `[DONE]`, then tears down the server. This diagnostic config does not establish production backend, long-context, tool-call or performance support.

Local contract tests: `python -m unittest discover -s tests -p 'test_spark26_gguf.py' -v` from the EvolveEngine repository root.

## Build and run the offline diagnostic E0 image

Use an authorized, otherwise idle linux/arm64 GB10 node. This image includes patched SGLang and the dependency overlay; the model and tokenizer stay outside the image. The pre-existing base provides the unchanged transitive/CUDA stack; verify its exact image ID (the build script checks it), not a mutable tag. This is a dependency-image lock for the **diagnostic** configuration, not an assertion that all backends work.

1. Prepare a fresh Docker build context. Copy `Dockerfile.e0`, `SHA256SUMS`, `apply_overlay.py`, `spark2_5_gguf.py`, `e0_entry.sh`, and `e0_probe.py` into it. Stage the exact fixed-revision source as `sglang.tar.gz` and the wheel files listed in `SHA256SUMS` under `wheels/`. Do not add unlisted wheel files; the lock is for the 13 listed wheels, not partial downloads or a fresh resolution from `pip`.
2. Check `(cd "$context" && sha256sum -c SHA256SUMS)`, then run `bash build_e0.sh "$context" "$base_tag" "$candidate_tag"` with authorized Docker access. The build does not pull a base or resolve dependencies on the network. Record the result of `docker image inspect --format '{{.Id}}' "$candidate_tag"` and run by that image ID. A portable Docker archive, if exported, should have its own SHA-256 and be verified after transfer; building from the listed inputs does not promise byte-identical layers across builder versions.
3. Use only the matching config/tokenizer/chat template and the already audited Q8_0 weight identity `d1df86f9332b75424ab3f7e14fdc2cf20aec93fa1e4a86393bb4e75057f24180`. After checking model provenance, mount the model directory read-only as `/model`; it should provide the Q8_0 file at `/model/Spark-X2.6-1.7B-Q8_0.gguf` (an additional read-only file bind may supply it). No host code, wheel or cache mounts are needed.

```bash
docker run --rm --network none --gpus all --shm-size 2g \
  --mount "type=bind,src=$model_dir,dst=/model,readonly" \
  "$image_id" quality
# Only after the same image and model pass the quality run:
docker run --rm --network none --gpus all --shm-size 2g \
  --mount "type=bind,src=$model_dir,dst=/model,readonly" \
  "$image_id" bench
```

`quality` emits named API checks on stdout and the server log on stderr. `bench` and `bench reverse` measure concurrency 1 and 2 in opposite orders, eight requests per block with warm-up excluded. Reported latencies are client-observed on loopback; TTFT means first content event, and TPOT is an estimate from first/last content event divided by the reported token intervals. Block token throughput uses completed output tokens divided by block wall time. With only eight requests, nearest-rank p95 equals that block's maximum; treat it as descriptive, not a production tail estimate. The configuration deliberately disables the radix cache and both CUDA graphs and uses short synthetic traffic. It does not establish production workload, FlashInfer support, tool-call quality, or long-context behavior beyond the tested 1K configuration.

## Separate first joint prefill from warm state

On the exact archived diagnostic image, use `batch_probe_entry.sh` as a read-only mounted entrypoint together with `batch_probe.py` under `/diagnostic/`. `warm_chat_probe_entry.sh` + `warm_chat_probe.py` are a separate no-additional-probe experiment: they use the baked E0 launcher unchanged and compare ordinary channel warmup against one explicit two-sequence startup prefill before the timed chat requests. Fresh containers, counterbalanced `control / primed / primed / control`; retain request/summary rows and server logs. Use `python warm_chat_audit.py <chat-study-directory>` to count true two-sequence prefill in the server-log phase markers before interpreting results. Record startup prime time separately, and do not attribute output differences or all live traffic to this synthetic workload.

## Synthetic calibration and separate diagnostics

See `TARGET_PILOT_LOCK.md` for the safety boundary and open gates. `calibration_workload.json` specifies warmed E0/E0 pairs over four native streaming shapes. Mount `synthetic_baseline.py`, `synthetic_baseline_entry.sh` and the workload file read-only under `/diagnostic`; each label runs in a fresh isolated container with the baked launcher. Save `<label>.stdout` and `<label>.server.log`; `python synthetic_baseline_audit.py <evidence-dir>` checks real batch size, output token counts/hashes and timing before summarizing per-process pairs. With three pairs, report descriptive variation only.

Use the `profile` label in a different container with a dedicated writable `/profile-out`. That container generates an ephemeral loopback-only admin credential; the timed labels never enable it. Preserve the staged `short1`/`long2` prefill/decode traces and `profiles.sha256` (relative paths `profiles/...`) with the server log. `python gguf_trace_audit.py <evidence-dir>` verifies hash coverage and reports actual GPU names, summed kernel durations and available CPU/GPU launch correlations. Do not treat trace sample percentages as production timings or infer unobserved fallback from names alone.

`deterministic_probe_entry.sh det1` and `deterministic_probe_entry.sh det2` use two fresh isolated containers and the diagnostic launcher with deterministic inference enabled. Mount the deterministic and synthetic Python files including `synthetic_baseline_audit.py` under `/diagnostic`. Keep `<label>.stdout` and `<label>.server.log`; the probe first reruns the six chat checks, then compares actual templated English, Chinese and bounded longer input IDs in native requests, including lane/order and real co-prefill. `python deterministic_probe.py audit <evidence-dir>` verifies the effective flag and token/finish consistency. These checks are separate from performance.

`runtime_residency_entry.sh` is a separate E0 diagnostic only. Inside a disposable container it adds two observation points to the image's private SGLang code; do not mount writable host source. Mount the workload and probe/client scripts at `/diagnostic`, retain the loopback server log, then run `python runtime_residency_audit.py <server-log>`. It requires three matching inventories and stable live allocation after warmup, discloses non-model allocator bytes, and does not certify native allocation provenance. Do not use it in a timed arm.

`allocator_residency_entry.sh` enables allocator stack capture in a separate residence probe. Preserve `residency.server.log` and use `allocator_residency_trace.py` to reconcile all Torch active bytes, padding, known model storage and grouped non-model allocations. This evidence does not enumerate direct/native allocations outside the Torch allocator.

`reference_coalesce.py` is a source-hash-checked **candidate preparation script only**. It patches just the fixed revision's `gguf.py` in a disposable root, requires the precise QKV/gate-up Q8_0 layouts and keeps the same dispatch class. `reference_coalesce_entry.sh` runs diagnostic shadow-equality and residence checks without timing. Use `reference_shadow_audit.py <candidate-dir> <e0-residency-log> <e0-e0-dir>` with the raw artifacts. `QKV_MICRO_PLAN.md` and `qkv_micro_lock.json` freeze an offline pinned-GGUF microbenchmark (actual packed shards, separate synthetic BF16 activations); parse with `qkv_micro_audit.py`. ## Observe the Chat application wire (isolated E0 only)

`chat_sse_observer.py` checks the pinned, single-choice `/v1/chat/completions` SSE contract on loopback. It records first generated payload (including reasoning or a tool event), first answer (content or a tool event), last payload and `[DONE]` separately. Role and usage frames are not generated payload. Require the terminal choice, final usage, matching request identity and a complete SSE close marker. The semantic digest merges chunk fragments without volatile response/tool IDs; it is not token-ID parity. The observer does not infer TTFT/TPOT from SSE frame count. The tool arguments are validated data only and are never executed.

In the same authorized idle-node diagnostic image, bind `chat_sse_observer.py`, `chat_sse_smoke.py` and `chat_sse_smoke_entry.sh` read-only at `/diagnostic`, use no host port/network and run `bash /diagnostic/chat_sse_smoke_entry.sh`. Archive the pinned bundle and logs, then run `python chat_sse_audit.py <evidence-dir> --bundle-sha256 <pre-run-sha>`. On November 23, 2026 the `.108` run passed text stop, length cap, separated reasoning/answer and a named tool call. These are four one-off conformance cases, **not** a production latency or E0/E0 measurement. Production equivalents must still declare which payload counts toward their latency SLO and how token timing is observed if needed.

## Revalidate on another node

Use `bash replay_archived_e0.sh <docker.tar.zst> <readonly-staging-dir> <exact-q8.gguf> <new-evidence-dir>` from an authorized idle GB10 node with Docker/GPU access. Keep `diagnostic-e0-model.sha256` next to the script. The model staging directory must already contain a regular file at the expected GGUF path (an empty bind placeholder is sufficient); the runner will not create or overwrite model files. It verifies the full archive and model identity, records whether the expected image was already present, loads the archive without overwriting an unrelated image tag, and only runs loopback `quality` with no external network. A node must pass its own replay before contributing performance data; never substitute cross-node E0/candidate rates for within-node comparisons.

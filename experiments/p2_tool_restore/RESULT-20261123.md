# P2 / 跨会话工具恢复夹具：成功轨迹与不稳定性（2026-11-23）

**最终登记的两次复测（05、06）均完成了五会话恢复；不签收完整 P2。** 本地模拟模型给出固定源码，真实 Pi 1.5.2 发起真实 `write/read` 与扩展工具调用。这里检验的是实际文件、装载和调用，不是模型自主发明工具，也不是针对任意不可信扩展的安全证明。全部为合成数据，未占 GPU、未调用付费模型。

## 五会话轨迹（04、05、06 各自完成一次）

| 会话 | 观察证据 |
|---|---|
| S1-B2 / S1-B0 | 接到同一脚本化工具调用，分别在新目录用实际 `write` 写出同字节的 `bad.mjs`。只有 B2 写出的文件进入按内容摘要索引的训练工件库。各自会话目录随后销毁。 |
| C1 | 新进程从存储的字节安装 H_bad。外部回环见证服务收到装载回执，模型请求的有效工具清单含 `count_hits`。工具对有匹配输入返回 2，零匹配输入触发预设错误；两次真实调用均通过调用 ID 和新鲜随机挑战核对。 |
| B | 从固定 H0 开新进程，用与 C 相同的启动工具允许名单；实际出站工具清单中没有 `count_hits`，但能 `read` 同一条公共事实。**这不是**对 B 重建或手动调用未注册工具的完整测试。 |
| C2 | C1 与 B 销毁后，从同一冻结摘要再次启动。原工具重新注册；含匹配输入仍返回 2、无匹配仍失败。外层没有把失败抹掉、也没换成另一个版本。 |

每条完整轨迹：5 个独立 Pi 进程、14 个模拟模型请求、4 个恢复后工具调用（成功 2 / 预设失败 2）；共同工具定义摘要一致，所有请求都在外部核对 `deepseek-flash`、Thinking enabled / Max、输出 cap 4096。外部见证只在**已核对的已知夹具**上有此解释；不能用扩展自报证明 T6 或推断真实 token/GPU 成本。

## 传输诊断与两次预登记复测

- 单独固定重放 S1 六次，[诊断回执](./s1-diagnostic.json)中五次完成、一次在首个请求后报告 `Connection error.: read ECONNRESET`。这给出了一个可核对的本地传输错误，不足以给 01–03 的所有未完成轨迹归同一个因。
- 按[05/06 事前登记](./TRANSPORT-05.md)，仅将本地模型服务由默认 HTTP/1.0 改为 HTTP/1.1 长连接并记录连接序号，未放宽 55 秒超时或更改判据。两次预定复测 [05](./receipt-05.json)、[06](./receipt-06.json) 均为 `pass_scoped`。两份回执中，S1-B2、S1-B0、B 的请求都使用各自会话的 `[1,1]` 号连接，C1、C2 各为 `[1,2,2,2]`；能观察到连接复用，但不是每一轮都在同一个连接上。
- 运行期间服务端仍在等候后续请求时报告过连接重置；05/06 规定的模型请求、工具结果和外部见证均完整。两次完成不能证明已消除所有传输错误，也不与此前不同配置的结果合并估计成功率。

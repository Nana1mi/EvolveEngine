# 框架 v3 设计：可信外层 + Agent 自建 Harness

本文是 [05 框架 v2 设计](./05%20框架%20v2%20设计.md)（v2.2）的后继草案。**v3 尚无实验结果**；星火先导只作工程校准。预算、样本量和会话长度待 E0 校准后再定（§9）。

**研究目标：** 训练时，Agent 能否自己构建有用的 Harness？评估时，把训练结束的 Harness 冻结，检验它在相同模型、引擎起点、结构化历史事实和续跑预算下，能否提高留出起点上的合法交付吞吐。**只配对起点，不配对过程；冻结可继承的 Harness，不冻结会话内的探索。**

**目标系统：**
- SGLang，提交锁定（诊断 E0 候选 `b2ce7f88`），加 Spark-X2.6-1.7B GGUF Q8_0；
- 运行在独占的 GB10 节点上；
- 参见 vault《SGLang + 星火 1.7B 目标先导》与 `experiments/spark26_gguf/`。

**与 v2.2 的关系：**
- 保留：账本、预算记账、密封的 Q/T 分区、独立裁判、来源与谱系、在留出母链 checkpoint 上评估冻结策略（RQ-A 的思想）、按谱系计算的置信区间。
- 放弃：固定流程"剖析 → 生成 ≤4 个候选 → 排序 → 实现"；"H 只能学排序"的设定；D/C 中"同选同执行"的耦合。v3 只配对**起点**，不配对中间执行。
- **v3 新建实验入口**，复用底层可信模块（§11），不往 `rqa.py` 里加条件分支。v3 生效前，v2.2 仍是现行协议。

## 1. 对象定义

| 符号 | 是什么 | 由谁写 | 在哪里持久化 |
|---|---|---|---|
| **E** | Engine：登记路径内的 SGLang 源码、kernel 和必要配置 | Agent | 引擎检出（§5.2） |
| **M_E** | 结构化引擎经验 | **控制器**按固定格式从账本生成 | 外层存储，只读注入 |
| **H** | Harness：Agent 自写的指令、笔记、Skills、工具、脚本、Pi 扩展、Workflow | Agent（仅 B0+ 和 B2，见 §4） | `agent_harness/`，由外层版本化 |
| **M_H** | Harness 经验：每次修改 H 的理由、预期、实际效果、回滚 | Agent 自写，外层附加客观回执 | 与 H 同一目录、同一版本 |

**M_E 的格式：** 每次尝试一条记录，字段如下：
- 父引擎摘要；
- 改动的文件和函数（外层从 diff 自动提取）；
- 已去掉注释和 docstring 的 diff，有长度上限。这里只处理记录本身，引擎源码不动；
- 枚举型动作类别、目标指标（如 decode 吞吐、TTFT）；
- 开发分区上的质量回执和计时回执；
- 结果（mainline / rejected / failed / timeout）；
- 枚举型拒绝原因码；
- 资源花费。

M_E **不设 Agent 自填叙述或附件字段**，不收假设、建议、经验总结。diff 仍含 Agent 写的程序文本，不声称完全消除了信息通道。两臂看到的历史事实是按同一规则生成的记录，而不是 H 私有笔记。

## 2. RSI 的操作性定义

| 层级 | 主张 | 最低证据 |
|---|---|---|
| **L1 自我修改** | Agent 自主产生 H₁ ≠ H₀ | 版本谱系中有非空、合法、可加载的 H 更新 |
| **L2 自我改进** | 修改后的 H 在留出起点上更有效 | RQ-A 中 H\* 优于 H₀（§6），**并且**评估会话里有生效证据 |
| **L3 递归改进** | Agent 用改进后的 H 继续产生有价值的新版本 | 谱系中 H_k 的产生依赖 H_j（j<k）的使用经历，且 H_k 优于 H_j（§8 次要对照）。不要求单调 |

**生效证据由外层记录，不依赖 Agent 自报。** 分三类：

| 类别 | 记录内容 |
|---|---|
| `loaded` | 提示/Skill 内容由 broker 将实际请求中的片段摘要绑定至来源版本；代码加载须有外层观察到的实际组件身份。清单、目录存在或 Pi 自报都不等于加载 |
| `available` | 外层记录工具注册或实际向模型公布的工具定义，绑定来源版本；与调用分开 |
| `invoked` | 外层观测调用，绑定工具身份、参数摘要和成功或失败回执；没有独立观测的事件标为未核验 |

**生效只说明该版本参与了运行，不能证明它改善了决策。** L2 的效果证据只能来自 RQ-A 的独立比较。

**措辞规则：**
- 只有 L1，只能说"能自我修改"；
- 有 L2，才能说"自我改进有效"；
- L3 成立，标题和结论才能用"递归"。

## 3. 架构与可信边界

**可信边界放在进程或容器之外。** B2 可以写 Pi 扩展，这些扩展和 `pi_guard.ts` 运行在同一个 Pi 进程里，可能绕过或干扰其他钩子。所以 Pi 守卫只算第一道检查，不能当作安全边界。

```
宿主 / 可信外层（Agent 容器之外）
  ├─ Provider broker：持有 API 密钥，执行 token 预算，核对实际请求并留存来源/片段摘要（用于 loaded 证据）
  ├─ 工具 RPC：profile / measure / quality → 受保护的 GPU Worker 容器
  │     只用开发分区；实现、负载、回执都不可修改；每次调用计入 GPU 时间
  ├─ 独立裁判：密封的 Q/T；冻结的质量门（可加检查、不可放宽）；在干净检出上重新起服务
  ├─ Journal：E/H 版本、谱系、会话日志、生效证据
  └─ Harness 安装器：合法性检查、版本快照、回滚接口（§5.1）
Agent 容器（每个会话新建）
  ├─ 锁定版本的 Pi + 同一个强模型（只能经由 broker 调用）
  ├─ 挂载：引擎检出（读写）、agent_harness/（按组别决定，见 §4）
  ├─ 网络：只通 broker 和工具 RPC；无密钥；无宿主机 root；看不到 Q/T
  └─ Pi 守卫（第一道检查）
```

**冻结的契约：**
- Q8_0 权重保持量化驻留；
- 完整词表；
- EOS 和长度语义不变；
- 业务负载固定，Agent 不能自己生成计时负载；
- 实验在独占节点上进行，现网只读；
- 第一轮只改 Python 和 Triton。

**正式的 Q/T 不作为优化反馈。**

## 4. 实验组与跨会话状态（按通道划分）

| 跨会话持久化 | B0 固定 Harness | B0+ 文本 | B2 开放 RSI | B1 人工 RSI（仅登记） |
|---|---|---|---|---|
| E | 保留 | 保留 | 保留 | 保留 |
| M_E（控制器生成） | 保留 | 保留 | 保留 | 保留 |
| 会话内的临时工具和脚本 | 允许，会话结束即清空 | 同左 | 同左 | 同左 |
| `agent_harness/` 中的文本文件 | 不保留，每次重建 H₀ | **保留** | 保留 | 由人工规则决定 |
| `agent_harness/` 中可直接加载或调用的组件（脚本、工具、Pi 扩展、Workflow 代码） | 不保留 | 不保留 | **保留** | 由人工规则决定 |
| M_H | 无 | 保留（文本） | 保留 | 由人工规则决定 |

**各组真正能跨会话复用的东西：**

| 组 | 可复用内容 |
|---|---|
| B0 | 只有控制器生成的结构化事实 |
| B0+ | Agent 自写的文本知识、指令和代码描述。文本里也可以写代码，下一会话可以复制出来执行 |
| B2 | 文本，加上**无需重建、可直接安装、加载、调用**的持久化执行组件 |

因此，B0+ → B2 的差异只能解读为"持久化、可直接复用的可执行 Artifact 带来的额外收益"，不能解读为"自写代码的全部价值"。"文本"和"可执行"由外层按加载路径和安装方式判定，不按扩展名判定（§12-5）。

**任务目标相同，持久化权限不同。** 两组使用同一优化目标、基础工具、预算和事实接口。训练提示只说明目标、能力和资源边界，不要求先总结、改 Workflow、造工具或按固定次序比较收益。B2 可以不改 H；B0 可以根据事实在本会话重建同类工具，耗费照计，这不算泄露。

**执行顺序：**
1. 先跑 B0 和 B2。
2. 只有当 B2 出现效果，并且 B2 的可执行组件在评估中确实被 `invoked`，才加 B0+。
3. B1 作为预登记的后续实验，现在不投入 GPU。

**配对的含义：** 分叉开始时，两组的 E 和 M_E 完全相同，M_E 的格式、生成规则和检索接口与预算也相同。第一次分歧之后，两组各自演化，**不共享动态经验**。

## 5. 通道泄露防护

### 5.1 Harness 的安装与回滚

- 外层**只检查合法性**：能否加载；有无越界写入；有无访问密封数据、网络或密钥；是否破坏工具 RPC 协议。**外层不按收益放行**，否则 B2 就变成了 B1。
- **仅训练阶段**开放持久提交、激活与回滚。是否使用这些接口由 Agent 决定；外层只按请求恢复已提交的合法版本。评估分叉没有这些写权限（§6.1）。
- 某个版本合法、却让 Harness 失效，这算 RSI 的一次真实失败：保留轨迹、照常计费、不替它恢复。违反契约的提交拒收并记账；Agent 自身导致的无合法交付按 §6.3 计分，不冒充设施故障重跑。

### 5.2 防止经由引擎检出夹带 Harness

**不改写已验证的引擎源码。** 原因有二：
- 外层改写会引入一个没经过同样质量验证的版本 E′；
- docstring 是运行时对象，Triton/JIT 和注册机制可能依赖源码的具体形式。

改为以下措施：
1. 交付只认登记路径白名单内的推理源码和必要配置。在 E 中新增笔记、Skills、Agent 配置或无关脚本，一律拒收。
2. 从 E 传给下一会话的，只能是已验收的 Engine Artifact，即通过质量门的原始 diff。
3. **静态审计**：检查新增的注释和 docstring 体量、大段字符串常量、从未被调用的函数、与推理无关的模块。超过事先登记的阈值，就判该次交付不合格，Agent 需在同一预算内修改。外层不代为删除。
4. 裁判在不含 `agent_harness/` 的干净检出上重新起服务。

**残余风险**：低于阈值的注释，以及藏在命名里的信息，无法彻底消除。报告中列为局限，并抽样审计估计其程度。"规范化注释"如果以后要做，必须作为独立特性单独验证语义和质量一致后，才能启用。

## 6. 主实验 RQ-A（确认性）

**问题：** 已提供同样的训练事实时，冻结的自建 Harness 是否比固定 Harness 交付更高的合法吞吐？前期学习成本不计入本对照，另在 RQ-B 报告。

### 6.1 训练、冻结与分叉权限

B2 从 E₀ 出发，在训练谱系 W 中只用开发分区。训练预算截止时，取 Agent **当前激活且已提交的合法版本**为 H\*，不追溯历史最优；若未改动，就冻结当时的 H₀。外层同时封存 W 的结构化事实库 $M_E^W$，供两臂按同一规则读取。

**冻结对象是可执行的整套环境，不只是 H 目录。** 外层为 H₀ 和 H\* 分别生成不可变清单：H、$M_H$（如有）、指令/提示、Skills、工具、扩展、Workflow，以及实际加载所需的传递依赖、加载配置和顺序、Pi 可执行文件与基础运行环境。记录内容摘要；分叉启动时核对实际解析的文件和版本，不能现场补取未登记依赖。共享的 Pi 和基础环境必须相同；H 专属组件随各自版本冻结。清单不匹配则不开跑，不静默替换。

| 状态 | 评估会话内可做什么 | 后续会话或其他分叉能看到什么 |
|---|---|---|
| H₀ 或 H\*、$M_H$、依赖与加载配置 | 从指定快照只读加载；无公共提交、激活或回滚权限 | 每次只加载该臂原冻结快照；已提交版本与激活指针均不变 |
| 临时脚本、工具副本、工作流、缓存、会话上下文 | 两臂都能创建、修改和执行私有副本，计入同一预算 | 会话结束即丢弃；不能进入其他会话的检出、检索、日志或工具列表 |
| E 与本分叉新增的 $M_E$ | 可探索、修改并按 §5.2 交付 E；$M_E$ 由外层生成 | 如同一续跑跨多个会话，只能按协议在**本分叉内**传递已验收 E 和结构化事实；不同分叉不交换状态 |

外层审计日志保留供研究者核验，不作为下一分叉的 Agent 上下文。评估期间允许 H 持久升级是另一个研究问题，不纳入 RQ-A。

### 6.2 起点和两个直接比较

B0 使用 H₀ 从 E₀ 独立生成留出母链，全程不接触 W。在每条母链墙钟预算的 50% 和 75% 各取一个 $(E,M_E)$。下表的 A/B/C 是**评估条件**，不是新增三种训练组。每个入选 checkpoint 只配对起点：任务、E、起点事实、基础模型配置、基础工具、资源上限和检索接口一致，不约束后续动作。

| 条件 | 继承的 Harness | 可检索的结构化事实 |
|---|---|---|
| A（可选） | 固定 H₀，无 $M_H$ | 起点 $M_E$；不开 W 事实库 |
| B（主对照） | 固定 H₀，无 $M_H$ | 起点 $M_E$ + 同一份 $M_E^W$ |
| C（处理臂） | 冻结 H\*，含训练时的 $M_H$ | 与 B 相同的记录、检索接口和预算 |

- **C−B：唯一确认性比较。** 估计同样训练事实之上，整套冻结 Harness 的增量作用；不把效果单归因于工具代码、笔记或工作流。
- **B−A：预算允许时的辅助比较。** 是否加 A、在哪些配对起点加，在看评估结果前登记；计算相同起点上开放 W 事实库的净效果，检索和上下文开销照计。不把它称为“纯经验收益”，也不根据两项比较是否显著来归因。不跑 A 不影响 C−B。

### 6.3 终点、失败与结论边界

独立裁判在密封 Q/T 上比较续跑终点的合法吞吐。每个 checkpoint 先算配对的对数吞吐差（主对照为 $\log r_C-\log r_B$），同一母链两个 checkpoint 的差等权平均，再以**母链**为单位求配对 95% CI 并换算成相对吞吐增益。主判据为区间下限 > 0；3% 仅作参考线。B−A 若开展，单独报告估计及区间，不改变主判据。

- 基础设施事件按事先登记的清单认定：节点故障、GPU 被抢占、broker 或裁判中断。受影响的配对按原起点重跑并记录次数；辅助臂单独故障不作废已完成的主比较。
- 开发和正式交付均区分三种状态：正确但变慢仍合法，允许 Agent 主动继承并按实测成绩计分；有已核实的违规证据则拒绝；证据不足则不签收、单列原因，不记作合法零收益。下条的起点计分只适用于已确认的 Agent 失败，不是缺回执的默认值。Controller 不替 Agent 按历史性能选 E 或 H。
- Agent 或 Harness 自身失败（工作流损坏、预算耗尽等导致无合法交付）保留、不重跑；无合法交付按起点引擎计分，成本照计。不能把最差的运行当随机缺失剔除。
- 若只有一条 W，结论仅针对**这个 H\*** 在同一目标系统、登记负载和留出起点上的迁移。更多 checkpoint 不是更多独立训练；宣称训练过程可重复或能跨任务迁移，需要新的 W 或真正留出的不同任务。

## 7. 成本与回本 RQ-B（描述为主）

**过程侧回本（主口径，单位一致）：** 先登记一个目标吞吐 $r_{\text{target}}$。在 RQ-A 的起点上测出两臂到达目标的搜索成本 $C_{\text{search}}$，以 GPU 时间和 token 计，换算到同一资源单位。则

$$N_{\text{break-even}}=\left\lceil \frac{C_{\text{train}}}{C^{H_0}_{\text{search}}-C^{H^*}_{\text{search}}}\right\rceil,$$

分母 ≤ 0 时不回本。$C_{\text{train}}$ 包括 W 的全部 GPU 时间、token 和 Harness 维护开销。某一臂在预算内没达到目标，就按截尾处理并如实报告，不外推。

**服务侧摊销（辅助，带假设）：** 若一次部署要处理 $Q$ 个输出 token，节省的服务 GPU 时间是 $\Delta C_{\text{serve}} = Q(1/r_0 - 1/r_*)$。没有真实流量规模时，只报几个假设规模下的摊销曲线，不给出单一回本数。并发、SLO 和延迟约束另外说明。

**当次比较：** 在同一总预算下，B0 和 B2 各从 E₀ 跑一条链，B2 的 Harness 开销计入预算。单节点上 n 很小，只作描述。

**随预算变化的曲线：** 在 25%、50%、75%、100% 预算点，分别报告：
- 最佳合法吞吐；
- 首次合法收益的时间；
- 有效尝试率；
- RSI 自身开销的占比。

RQ-A 为正，不能推出整个系统总成本为正，两者分开报告。

### 8.1 交付补丁的来源：事前定义，事后盲判

以冻结前 W 的**全部尝试**为参照，包括失败、拒收和未进入主线的改动。外层封存来源记录与补丁；审阅时只给去除收益、回执结果及组别标识的源码、父版本和必要的运行语义，不给最终吞吐、排序或所属臂。先按能独立解释的改动机制拆分，再按下列顺序判定。文本相似、同名函数或同属“QKV 融合”均不足以单独判同。

| 类别 | 匹配规则 | 允许的解释 |
|---|---|---|
| Replay（重放） | W 中已有可直接重放的补丁；只差上下文行号、格式等，不需改变实现逻辑 | 复用已有补丁，即使该训练尝试未获益 |
| Adapt（适配） | 能指出 W 来源；作用对象、关键操作及预期生效原因一致，但为不同布局、接口或前提改过实现 | 把已见机制适配到新引擎状态 |
| Novel（相对 W 未见） | 来源记录足以比较，且检索 W 全部尝试后，没有与该改动关键操作和生效原因对应的机制 | 只说明在此 W 中未见；单个样例不证明搜索方法改善或技术原创 |
| 无法判定 | 记录截断、机制不可拆分或审阅分歧无法消解 | 保留不确定性，不默认归为 Novel |

两名审阅者独立写下来源尝试 ID（无匹配则记检索范围）、判类及理由，分歧先在盲态下复核，再锁标签、揭示收益。混合交付逐项记标签，不把整份补丁抬为 Novel。**所有合法交付仍按原吞吐计分**，不按类别筛样、加权或拆算收益；未交付和失败照 §6.3 处理。先导用例不自动算 W 来源，除非按协议进入 W。

## 9. 预算与样本量：先测再定

E0 跑通后，先做与正式实验分开的校准，测出以下数据，再据此确定 W 的长度、母链条数、续跑预算和可达到的 n：
- 单次合法修改的完整成本：重启服务、CUDA Graph 捕获、质量检查、计时；
- 每节点小时能完成的可靠测量次数；
- E0 对 E0 的噪声；
- 小规模试跑时搜索轨迹的方差。

正式 W 的总预算用 $B_W=(T_{wall},T_{GPU},N_{input},N_{output},N_{episode})$ 表示；最多 10 次真正跨会话的机会，不要求产生 10 个 H，不强制逐轮均分。GPU 按独占节点时间单列，推理 token 属于输出的子项；开发评测额度另记。达到 10 轮上限或总预算耗尽时，冻结当前激活版本。两次自由先导后才定数额。

**在此之前不承诺对数或谱系数。** 目前只有一个独占节点，`.139` 是共享机，不用。

**正式模型候选与原预检方案（不阻塞先导）：**
- B0、B2 及后续各组**用同一个经过预检的强模型**。正式开始前锁定以下各项：模型 ID、接口、Pi 版本、系统提示和工具协议。

- 利益相关声明：本节由 Claude 起草，模型的最终选择应以预检结果为准。
- **预检规则（事先登记）**：两个候选用同一套小任务集，在同一 Pi 版本下比较以下五项，按登记的权重选定，然后锁定：
  - 工具调用成功率；
  - 大仓库导航与编辑成功率；
  - 一个已知可行改动的完成率；
  - 每次合法交付的 token 成本；
  - 失败类型。

  已有文献报告过显著的模型与框架交互效应，所以预检必须在 Pi 上做。
- **接口适配**：当前 broker（`deepseek.py`）只代理 OpenAI 兼容的 `/chat/completions`，并从 `prompt_tokens/completion_tokens` 计量。换成 Anthropic Messages 或 OpenAI Responses，都要改写 broker 的转发和计量逻辑，并重新测试，不能想当然地认为可以直接换。

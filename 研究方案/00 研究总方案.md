# 固定部署下，推理引擎优化器能否改进自己的搜索策略？

> **v1 文档。** 当前 RQ-A 的研究问题、取点和判据见 [05 框架 v2 设计](./05%20%E6%A1%86%E6%9E%B6%20v2%20%E8%AE%BE%E8%AE%A1.md) §8。旧报告仍按本版解释；修改协议只在本 Git 目录进行。

**要检验的命题**是在相同的引擎起点、正确性要求和总资源上限下，把历史优化轨迹转化为可执行的候选排序规则，能否让下一段搜索更早找到有效补丁，并最终交付更快的引擎。首轮拟用 mini-sglang、Qwen3-0.6B 和一张 H100 80GB。固定的是起始实现、服务模型、硬件与请求分布，引擎源代码在实验中持续演化。

这套方案面向一个具体决定：**为一次策略改写花掉的 GPU 时间和模型调用，是否比把同样的资源再用于一次引擎优化更合算？** 最终用真实引擎的输出 token/s 回答。目录里的论文数字是设计背景，本项目目前没有 GPU 实测结果。

## 1. 一轮搜索具体做什么

单个 Coding Agent 首先给当前引擎做开发侧性能剖析，提出若干带有目标部位、预期信号和预计成本的候选，例如减少主机发射开销或调整一次访存。固定控制器封存候选池，Harness 给它排序。Agent 对排在前面的可行候选写补丁。开发裁判编译、验证真实推理路径、测量耗时，控制器保存代码差分与带成本的原始记录，下一轮继承可用代码和报告。

强基线已经会看 profiler、跳过不可行候选、重测噪声较大的改动和保留最佳合法引擎。它的排序规则按瓶颈匹配程度、估计成本和固定次序选择。实验组从同一规则启动。它多一个能力：固定的更新器可以从过去的开发轨迹中提出一条新排序规则，让规则先在独立开发分叉上接受检验，通过后才进入主线。之后在一个全新会话中，给定同一组候选和同一份状态，规则仍可改变执行顺序。

例如，两项主机侧改动都与当前瓶颈匹配，便宜的队列整理在 H0 下排第一。如果既往轨迹提示，观察到明显 launch gap 时，减少发射次数的候选更值得先试，更新器可以提议一条有条件的优先规则。这条规则有三个可以逐一查验的后果：触发时排序改变，执行后相应的间隙指标按预测变化，最终合格引擎在等预算续跑中受益。任何一环都可能失败。一次排序回放只能检查第一环。

## 2. 把三种改变分开保存

| 对象 | 每次保留下来的东西 | 要回答的问题 |
|---|---|---|
| 引擎 E | 起点、补丁、构建环境、质量门禁回执、复测后的可交付版本 | 相对于共同 E0，交付物能快多少？ |
| 经验 M | 含失败在内的实验报告、profile 摘要、成本、记录来源 | 同一份报告交给两个版本，它们是否做出不同选择？ |
| Harness 策略 H | 可执行排序规则、父版本、提出时可见的轨迹、晋级或拒绝记录 | 只替换排序规则，后续优化能力是否改变？ |

固定更新器 U0 读取开发轨迹、提出 H 的变更。独立的实验控制器持有验证数据、资源账本和晋级权限。模型、工具能力、候选生成接口、跨会话记忆读取方式和强制质量门禁在主比较中都冻结。这样，发现新 Kernel 可以记入 E 的成果，发现新的候选优先条件可以记入 H 的成果，各自都有可回放的版本。

排序是第一个开放的接口。它的输入和输出可以封存，也能在两个策略间交换。若同时让系统改写 profiler、生成候选、扩充工具、重新分配硬预算，即使最终引擎变快，也难以定位哪个机制值得保留。工作流、经验检索和软预算分配可在首轮之后各自做单因素实验。

## 3. 三个实验问题

| 问题 | 对照与测量 | 能支持的判断 |
|---|---|---|
| **RQ1　自改策略是否值得付费？** | 从同一 E0、H0 和初始记忆建立配对独立链。两组都继承引擎和报告。固定组继续搜引擎，实验组可用自己的同一份预算生成、试验和更新排序器。截止时先锁定各自唯一交付版本，再做同分布盲测。 | 整个方法在指定预算和部署下的净收益。两条链之后各自形成的代码与历史自然会不同。 |
| **RQ2　新策略本身有用吗？** | 在事先独立建库的同一 E、同一 M 和同一首轮候选池上，交叉装入冻结的 H0 或最终 H*。两边获得同样的新预算，关闭进一步策略更新。按独立谱系汇总早、中、晚检查点的续跑结果。 | 控制起点后的策略版本效应。第一步以后允许两条轨迹自然分化。被选中策略的开发晋级数据不能兼作这项证据。 |
| **RQ3　收益依赖什么？** | 在相同检查点交叉开关跨会话历史与排序策略，再用禁用单条规则的回放及独立续跑检验触发条件。所有分支保留会话内反馈。 | 区分记忆收益、可执行规则收益和两者交互，并定位受益或受损的瓶颈状态。 |

主终点取预算截止时实际可部署引擎的盲测吞吐相对起点的比值。次要读数包括最佳开发合法引擎随预算的曲线、达到预设目标花掉的资源、有效补丁率、错误类型以及更新器本身的开销。一次吞吐测量可以重复很多次，但一次优化链仍只算一个实验单位。完整判据、未达标与回退计分见 [02 实验协议与判定规则](./02%20%E5%AE%9E%E9%AA%8C%E5%8D%8F%E8%AE%AE%E4%B8%8E%E5%88%A4%E5%AE%9A%E8%A7%84%E5%88%99.md)。

## 4. 第一次上机，先找排序可发挥作用的位置

1. **校准尺子。** 在准备好的目标机器上锁定版本、计时边界、精度、缓存和功耗设置。对未改动的 E0 走完开发与裁判路径，保存波动范围。加入会破坏 EOS、交错请求缓存或完整词表的受控测试夹具，确认质量门禁可以拦下。先导调整须在正式实验前完成。
2. **跑通固定组。** 从一次 profile 开始，生成候选、提交补丁、得到开发回执，然后换新会话从归档恢复。验收时应能重建引擎版本、重放选择、重算剩余预算，并找到一次失败是如何影响下一次决策的。
3. **估计排序有没有空间。** 只在隔离的先导数据上，抽取若干有多个可行候选的状态，从相同父版本分别试做前几个候选。记录首选是否经常落后、优劣能否超过重测噪声、实际成本是否与预估相符。该诊断消耗单列，不向正式链提供被比较补丁或赢家清单。如果多数状态只有一个可行动作，先修候选生成或改变研究切口，再开昂贵的确认实验。
4. **做最小配对试验。** 验证系统能自动提出规则、接受或拒绝规则、把成本记回实验组，并从相同快照隔离续跑。若没有候选策略晋级，也应能交付一条完整失败链，区分没有触发、没有行为变化、门禁失败和有作用但不划算。
5. **锁协议后进行确认。** 冻结先导之外的正式请求、独立检查点来源、样本量、预算和评分规则，生成配对运行清单。截止时按开发数据选版并锁定哈希，盲评后按已定规则一次性汇总。

第一版的可行性取决于盲测噪声、编译加测量的周期和实际候选池大小。如果单次构建就吃掉大半短续跑预算，比较测到的是“谁先编译完”。用先导实测重定两组共同的续跑长度，再锁正式方案。若预算只能支撑先导，报告可行性和效应范围。

先导拟跑 **4 对独立优化链**，主链、建库和独立续跑的预算上限合计 **44 GPU 卡时**，校准及独立测量另计。若配对对数差的标准差为 0.05，为分辨 3% 的吞吐差，正式实验的计算示例为 **25 对、325 GPU 卡时**，同样另计独立测量。这两个数用于预算规划。真正要上多少卡时，取决于先导测出的方差和每次完整编译、验证、测速所需的时间。

## 5. 读结果与下一阶段

| 整体净收益 | 同检查点策略效应 | 解释与下一步 |
|---|---|---|
| 达到预注册判据 | 达到预注册判据 | 支持固定部署下的 Harness 自我改进。结合规则触发及禁用实验，说明在哪些状态下有贡献。 |
| 达到 | 未达到 | 可以报告完整系统交付了更快的引擎。检查是否由少数引擎突破或偶然搜索路径驱动，策略归因仍待验证。 |
| 未达到 | 达到 | 策略对后续搜索有用，但在这份总预算内尚未回本。按元更新成本与续跑节省量同单位计算摊销，再预注册更长预算。 |
| 未达到 | 未达到 | 按候选是否多样、排序是否改变、补丁是否落地、门禁是否通过逐层定位。区间过宽记作不确定，方向稳定为负则报告退化。 |

跨部署迁移可以另开一项实验。冻结学到的 H，从干净 E0 启动，在预先留出的负载、硬件或引擎上重新优化。首轮结果据实使用“任务特定的 Harness 自我改进”这一名称。

### 何时值得把更新器自身纳入实验

若已有多次可复现的 H 更新，就有机会问一个更高阶的问题：系统能否改进“怎样提出下一条规则”？可先开放 U 中**选择哪些成功与失败轨迹配对**这一处决策。策略规则语法、候选数上限、总元预算、晋级门槛和最终裁判继续固定。这样能追踪 U 的一次更新究竟改变了它看到的证据，还是只碰巧继承了已有的好 H。

把系统生成的 U* 和原始 U0 冻结，各自从相同 H0 起步，读取同一份未参与更新器训练的历史，以相同总预算和提案机会产生后代 H。每一边只按开发数据选择一个后代，在另一批隔离检查点上比较后代继续优化引擎的能力。没有合格后代的一边交回父版并记为一次未改进。再把两版 U 移植到同一个已进化的父 H 上重复比较，检查优势是否仅限于它自己的谱系。报告固定提案数内得到至少一个有效改进的比例、后代的盲测收益、以及每次有效改进的元成本。只有当系统自主生成了 U 的持久变更，并且后代试验也支持增益，才有依据提出严格的递归改进主张。

## 6. 一次完整实验应交付什么

| 交付物 | 验收时可直接核查的内容 |
|---|---|
| 引擎与实验清单 | 两组 E0 相同，最终交付引擎各有唯一哈希，能从干净环境重建。硬件、请求分布、模型权重、Agent 模型和评测协议均有标识。 |
| 策略演化记录 | 每个规则可追溯到父版本、提出它的轨迹、开发验证和每笔费用。拒绝的规则也在记录中。 |
| 净收益图 | 各链的盲测终点，以及开发侧最佳合法性能随累计花费的阶梯曲线。图上标出提议、验证和晋级，不把开发曲线当作盲测曲线。 |
| 因果与反例 | 同检查点配对差值、区间和分层结果。附一条成功或最接近成功的轨迹，以及一条规则被拒绝或造成退化的轨迹。 |
| 成本与质量报告 | 分开列模型输入/输出、卡时、编译、验证开销和失败数，列出 EOS、全词表、交错请求及独立质量检查。读者可以复算每个正式结论。 |

当前目录提供研究设计、工程规格、预注册草案和一个离线契约实例。真实引擎与 Agent 接入、权重及请求清单准备、计时校准和正式运行均列为实施阶段工作。
